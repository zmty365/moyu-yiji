# 摸鱼成就系统 · 数据存储方案对比

> 配套 [`achievement-prd.md`](achievement-prd.md)。本文专门讨论**数据存哪里、会不会丢、如何选型**。
> 背景问题：用户删除浏览器缓存、卸载重装插件、换设备时，成就/统计数据是否会丢失。

## 0. 结论先行

- 现状（localStorage / chrome.storage.local）都是**浏览器本地存储**，用户主动清理或卸载会丢，且不跨设备。
- 你提出的"数据直接存在插件本地"**不是新方案**——它就是扩展版已在用的 `chrome.storage.local`（本身就存在插件本地）。
- 但确实还有几种**机制层面不同**的存储方式之前没列全（IndexedDB、真实文件、session）。本文把**全部 5+ 种**列出并对比。
- 推荐：**导出/导入 JSON**（解决丢失）+ 扩展版可选 **sync 存汇总**（跨设备恢复成就进度）。

## 1. 丢数据的三个场景（先明确风险）

| 场景 | localStorage（网页版） | chrome.storage.local（扩展版） |
|---|---|---|
| 清除浏览器缓存 / 网站数据 | **大概率清空** | 相对安全（清缓存一般不动扩展存储） |
| 卸载插件再重装 | 不受影响（与插件是两套） | **必定清空**（卸载会删扩展全部 storage） |
| 换设备 / 换浏览器 | 不同步 = 没有 | 不同步 = 没有 |

## 2. 所有可选存储机制对比（含"第五种"澄清）

| # | 机制 | 属于谁 | 卸载扩展 | 清浏览器数据 | 跨设备 | 容量 | 读写 | 适用性 |
|---|---|---|---|---|---|---|---|---|
| 1 | `localStorage` | 网页版 | 不影响 | **易丢** | 否 | ~5MB | 同步 | 网页版现状 |
| 2 | `chrome.storage.local` | 扩展本地 | **丢** | 较安全 | 否 | ~10MB(可提额) | 异步 | 扩展版现状 |
| 3 | `chrome.storage.sync` | 扩展+账号 | 丢本地但**可随账号恢复** | 较安全 | **是** | **总~100KB / 单键~8KB** | 异步 | 存汇总量 |
| 4 | `chrome.storage.session` | 扩展内存 | 丢 | — | 否 | ~10MB | 异步 | 仅本次会话，**不适合** |
| 5 | IndexedDB | 网页/扩展 | 扩展内会随卸载丢 | 易丢（同 localStorage） | 否 | 大（数百MB+） | 异步 | 明细多才需要，当前**过度** |
| 6 | 导出/导入 JSON 文件 | **用户手里** | **不丢** | **不丢** | 手动带走即可 | 无限 | 手动 | **最可靠的兜底** |
| 7 | File System Access API | 磁盘真实文件 | 不丢 | 不丢 | 否 | 大 | 异步+需授权 | 每次要用户授权，体验重 |
| 8 | 云端账号 + 服务器 | 服务器 | 不丢| 不丢 | **是** | 无限 | 网络 | 需登录/后端/隐私合规，**严重过度** |

> **关于"第五种：数据直接存在插件本地"**：这正是表中 **#2 `chrome.storage.local`**，它天然"存在插件本地"，并非新方案。真正机制不同的"额外选项"是 IndexedDB(#5)、真实文件(#7)、session(#4)。

## 3. 为什么 sync 不能无脑全塞

摸鱼数据是**逐日一条 key**（`moyu-log:2026-08-08` ...）。`chrome.storage.sync` 总量约 100KB、单键约 8KB、且有写入频率限制。天数一多必然超限。
**因此 sync 只适合存"汇总量"**（总秒数、打卡天数、最长连击、已解锁成就 id 等几个数字），不能存逐日明细。

## 4. 四种应对方案（对应你要的"列出四种方法"）

### 方案 A：接受现状，不做任何持久化增强
- 成就/统计视为纯本地娱乐数据，丢了就丢。
- 成本：零。适合"就是个摸鱼小玩具"的定位。

### 方案 B：导出 / 导入 JSON（推荐，性价比最高）
- 加两个按钮：导出把全部 `moyu-log` + 设置打成一个 JSON 让用户保存；导入可恢复。
- 覆盖**全部丢失场景**（卸载重装、换设备、清缓存），因为文件在用户手里。
- 成本：低（两版各加几十行），无后端、无隐私负担。

### 方案 C：扩展版把"汇总数据"存一份到 chrome.storage.sync
- 只存汇总量（见 §3），随 Google 账号跨设备 / 重装恢复"成就进度"。
- 局限：逐日明细（30天柱状条）仍会丢；需处理容量与多端冲突。

### 方案 D：接云端账号 + 服务器
- 最可靠、可跨端，但要登录/后端/隐私合规，对摸鱼工具**严重过度设计**（违背 KISS）。不推荐。

### 补充：第五种机制方案 E（IndexedDB / 真实文件）
- IndexedDB：容量大，但**丢失特性和 localStorage 一样**（清数据/卸载照样丢），只在明细数据量很大时才有意义——当前场景**过度**。
- File System Access：能落地成磁盘真实文件、最不易丢，但每次访问要用户授权，交互重。可视为方案 B 的"自动文件版"，非必要不上。

## 5. 各方案能否解决三大场景（速查）

| 方案 | 卸载重装 | 清浏览器数据 | 换设备 | 复杂度 |
|---|---|---|---|---|
| A 不处理 | ✗ | ✗ | ✗ | 无 |
| B 导出/导入 | ✔(手动) | ✔(手动) | ✔(手动) | 低 |
| C sync 汇总 | ✔(仅汇总) | ✔(仅汇总) |✔(仅汇总) | 中 |
| D 云端 | ✔ | ✔ | ✔ | 高 |
| E IndexedDB | ✗ | ✗ | ✗ | 中 |
| E 真实文件 | ✔ | ✔ | 需手动 | 中高 |

## 6. 推荐

- **主选方案 B（导出/导入 JSON）**：一次投入，解决绝大多数丢失场景，零后端零隐私风险。
- **可叠加方案 C**：仅扩展版、仅同步汇总量，给"成就进度"加一层跨设备恢复。
- 明确**不做 D**（过度）、当前**不做 E**（收益不抵成本）。
